# 16 — AI Floor Plan & Apartment/Unit Segmentation (Phase 4)

> **AI_DEMO / MODEL OUTPUT / DEMO_RESEARCH_DATA (dataset: CubiCasa5K).** This is
> an **AI research/demo pipeline**. It does **not** produce legally authoritative
> cadastral or property-unit boundaries. Floor-plan geometry, room labels and
> apartment/unit boundaries are automated model output, never official Tamil
> Nadu cadastral, Chennai building-approval, ULPIN, ownership or
> government-approved apartment-boundary data. Unit/room identifiers are
> prototype application IDs (`AI-UNIT-nnn`, `FP-RM-nnnnnn`) — **never** official
> ULPINs. Human review is required before any authoritative use.

Additive to Phases 1–3. If the Python `ai-service` is unavailable, the endpoint
returns `INFERENCE_UNAVAILABLE` and the rest of the app is unaffected.

```
Floor Plan Image
  ─▶ Python ai-service (/floorplans/infer)
       preprocess ▶ segment (wall probability) ▶ wall mask ▶ rooms
       ▶ topology (doors/openings) ▶ unit inference ▶ validation
  ─▶ Node /api/ai/floorplans/infer
       file validation ▶ job ▶ building/floor association (local -> WGS84 fit)
       ▶ aiFloorPlans + aiRooms + aiFloorUnits (MongoDB)
  ─▶ existing ONE Chennai-wide Cesium viewer
       (layer: "AI Floor Plans / Property Units", OFF by default)
```

## 3. Model selection

| | Default — `classical-cv` v1.0 | Optional — `semseg` |
| --- | --- | --- |
| What | local-contrast wall-ink response (`skimage.filters.threshold_local`) + morphology → per-pixel WALL probability | a semantic-segmentation head (`segmentation-models-pytorch`), e.g. DeepLabV3+/ResNet-34 or U-Net |
| Weights | none | `FLOORPLAN_SEMSEG_WEIGHTS` (a `.pt` file you train/obtain) |
| Deps | numpy + scikit-image (already required; scipy ships with it) | `torch`, `segmentation-models-pytorch` (**not** in `requirements.txt`) |
| Enabled | always | only when `FLOORPLAN_MODEL=semseg` **and** torch + weights are importable/present |
| Fallback | — | if torch/weights missing, the pipeline logs a note and uses `classical-cv` (never crashes) |
| If neither runs | pipeline returns `status: "MODEL_NOT_AVAILABLE"` | |

**Why the classical default:** deterministic, no GPU/weights, keeps CI light,
and gives a working inference path immediately (the spec's "the application
MUST NOT require training every time it starts"). **Why DeepLabV3+/ResNet-34 is
documented as the primary upgrade path** (`configs/floorplan_segmentation.yaml`),
with U-Net as the lighter fallback architecture:

| Criterion | DeepLabV3+ (ResNet-34) | U-Net / U-Net++ | SegFormer |
| --- | --- | --- | --- |
| Accuracy on dense multi-class room layouts | atrous spatial pyramid pooling captures multi-scale room shapes well | strong on clean binary/few-class masks, competitive with enough data | strong, but needs more data/compute to beat CNNs at this scale |
| Inference speed (CPU-feasible prototype) | moderate | fast (lighter decoder) | slower without a GPU |
| Memory | moderate | low | high (transformer encoder) |
| Implementation complexity | moderate — `segmentation_models_pytorch` provides it directly | low | higher — needs a transformer runtime |
| Pretrained weights availability | ImageNet encoders widely available via `smp` | very widely available | available but heavier to fine-tune for a small dataset |
| Suitability for floor plans | good — floor plans mix large regions (rooms) and thin structures (walls) at different scales | good for wall/room binary masks; multi-class room typing is a stretch without more capacity | promising but overkill for a prototype with no training budget here |

Training config: `ai-service/configs/floorplan_segmentation.yaml` (documentation
+ starting point — **the application does NOT run training**). Evaluation:
`python ai-service/scripts/evaluate_floorplans.py --images DIR --masks DIR` →
wall-mask IoU / Precision / Recall / F1 / Dice + a room-count delta.
**Dataset evaluation ≠ Chennai deployment validation** — see §16.

## 4. Class mapping (`app/floorplans/classmap.py`)

Normalised application classes (`app/floorplans/config.py: APP_CLASSES`):

```
WALL · ROOM · CORRIDOR · DOOR · WINDOW · STAIR ·
BATHROOM · KITCHEN · BEDROOM · LIVING_ROOM · OTHER
```

Raw model labels are **never** assumed to match these. An explicit table maps
each vocabulary onto `APP_CLASSES`:

| Model vocabulary | Example raw label | → APP class |
| --- | --- | --- |
| `cubicasa5k-rooms` | `Kitchen`, `Bed Room`, `Bath`, `Living Room`, `Entry`/`Hallway`, `Stairs` | `KITCHEN`, `BEDROOM`, `BATHROOM`, `LIVING_ROOM`, `CORRIDOR`, `STAIR` |
| `cubicasa5k-icons` | `Door`, `Window`, `Toilet`, `Bathtub` | `DOOR`, `WINDOW`, `BATHROOM` |
| `classical` (the default heuristic) | `wall`, `space`, `opening` | `WALL`, `ROOM`, `DOOR` |

Unmapped labels fall back to `OTHER` — never dropped silently. `GET
/floorplans/config` exposes the full mapping for inspection.

## 5. Coordinate / georeference principle

A floor-plan image has **no geographic coordinates**. The pipeline distinguishes:

- **A. Non-georeferenced floor plan** (no `buildingId` supplied) — geometry is
  kept in a LOCAL coordinate system: `crs: "LOCAL_FLOORPLAN_PIXEL"` (pixels,
  origin top-left, y-down) or `"LOCAL_FLOORPLAN_METRE"` once a
  `scaleMPerPx` is supplied. `coordinateReference` on every response documents
  the origin, axes and scale. **No latitude/longitude is ever invented.**
- **B. Georeferenced / associated floor plan** (`buildingId`, optionally
  `floorId`, supplied) — the Node layer (`services/aiFloorPlans/associate.js`)
  fits the floor plan's pixel bounding box onto the **existing** building
  footprint's bounding box (a documented affine approximation — never assumed
  1 pixel = 1 metre) and reprojects every unit polygon into WGS-84. Result:
  `crs: "GEOREFERENCED_VIA_BUILDING"`, `geoStatus`. Floor elevation/height come
  **only** from an existing `floors` record (`floor.baseHeight`/`topHeight`) —
  never fabricated; if absent, `zmin`/`zmax` stay `null` and `heightStatus:
  "UNAVAILABLE"`.

Pixel↔metre scale is **only** used when `scaleMPerPx` is explicitly supplied by
the caller; otherwise every area is `areaUnit: "PIXEL_SQUARED"`,
`areaStatus: "SCALE_UNAVAILABLE"`.

## 6. Inference pipeline (`ai-service/app/floorplans/pipeline.py`)

1. **preprocess** (`preprocessing.py`) — sniff format (PNG/JPEG/TIFF, magic
   bytes checked, never the extension alone); reject unsupported / corrupt /
   empty / too-small; cap to `FLOORPLAN_MAX_IMAGE_PX` (ceil-step downsample,
   never a blind resize that destroys thin walls); tile to `FLOORPLAN_TILE_PX`
   with `FLOORPLAN_TILE_OVERLAP_PX` for large plans; normalise to grayscale
   float32 `[0,1]`.
2. **segment** (`segmentation.py`) — the selected backend's WALL probability
   per tile, stitched (mean over overlaps).
3. **walls** (`walls.py`) — threshold at `FLOORPLAN_WALL_DARK_THRESHOLD` →
   binary wall mask → morphological clean-up (bridges only tiny gaps, up to
   `FLOORPLAN_WALL_CLOSE_PX`, so unrelated walls are never over-merged) → wall
   region polygons + a skeleton-derived centreline per fragment.
4. **rooms** (`rooms.py`) — doorway gaps are **sealed** (wall dilation by
   `FLOORPLAN_ROOM_SEAL_PX`) before labelling connected free space so two rooms
   joined only by a door become distinct components; each room's true extent is
   then recovered by growing back into open space. Room TYPE is a documented,
   confidence-capped heuristic (size rank + aspect ratio) — replaced by real
   model classes when `FLOORPLAN_MODEL=semseg` is wired to a trained head.
5. **topology** (`topology.py`) — rooms whose polygons come within
   `FLOORPLAN_DOOR_ADJACENCY_PX` are linked by a DOOR/OPENING feature + a graph
   edge; nodes are tagged `room` or `circulation` (CORRIDOR/STAIR).
6. **units** (`units.py`) — connected components of **private** rooms only
   (circulation is never traversed) become apartment/unit candidates, scored by
   presence of a wet room (kitchen/bathroom), a living/sleeping room, and a
   plausible room count; ambiguous clusters get `reviewRequired: true`. Rooms
   that cannot be placed are returned as `unclassified`, never forced into a
   unit.
7. **validate** (`validation.py`) — see §9.
8. **3D volume** (`pipeline.py: _unit_volume`) — see §10.

## 7. Vector / polygon extraction

`app/floorplans/geometry.py` — connected components (`skimage.measure.label`) →
`find_contours` → `shapely.Polygon` → `simplify` → repair (`buffer(0)` then
`make_valid`, largest valid part kept; an unrepairable polygon keeps
`geometryStatus: "ERROR"`, never silently dropped). Stack: NumPy, Pillow,
scikit-image, Shapely — **no new hard dependency** (scipy ships with
scikit-image); GeoPandas/rasterio/pyproj are not needed here (no CRS math at
the Python layer — georeferencing is a Node-side bbox fit against existing
building data).

Each feature carries `featureId`, `class`, `polygon`, `area`, `confidence`,
`source: "AI_DEMO"`, `model`, `modelVersion`, `geometryStatus`,
`reviewRequired` — the exact shape requested by the spec.

## 8. Confidence (configurable, documented — no legal meaning)

| Level | Rule (env-overridable, shared with Phase 3) |
| --- | --- |
| `HIGH` | `confidence >= AI_CONF_HIGH` (default `0.80`) |
| `MEDIUM` | `AI_CONF_MED` (`0.55`) `<= confidence < AI_CONF_HIGH` |
| `LOW` | `confidence < AI_CONF_MED` |

Room-**type** confidence from the classical heuristic is additionally capped by
`FLOORPLAN_CLASSICAL_TYPE_CONF_CAP` (default `0.5`) so a heuristic label can
never claim unwarranted certainty. `reviewRequired = (LOW confidence) OR
(geometryStatus != VALID) OR (ambiguous unit inference)`. All thresholds live in
one place — `app/floorplans/config.py` — never duplicated across files.

## 9. Validation (deterministic — NOT AI)

`app/floorplans/validation.py` runs the full spec catalogue and returns
`VALID | WARNING | ERROR` with `rule`, `message`, `featureId`, `severity`:

| # | Check | Rule slug |
| - | --- | --- |
| 1–2 | invalid / self-intersecting polygon | `ROOM_GEOMETRY_VALID` / `ROOM_GEOMETRY_REPAIRED` |
| 3 | duplicate room geometry (IoU ≥ `duplicateIoU`) | `ROOM_DUPLICATE` |
| 4 | overlapping units (shared rooms) | `UNIT_ROOMS_DISJOINT` |
| 5 | overlapping rooms where inappropriate | `ROOM_OVERLAP` |
| 6 | gaps between expected unit boundaries (coverage ratio) | `UNIT_BOUNDARY_GAPS` |
| 7, 9, 10 | unit outside building / floor outside building / incorrect floor association | `UNIT_INSIDE_BUILDING` (Phase-2 `geometry3d`), `FLOOR_BELONGS_TO_BUILDING` — enforced in `services/aiFloorPlans/associate.js`, the layer that holds real building geometry |
| 8 | room placed in no unit / common area | `ROOM_IN_A_UNIT` |
| 11 | non-positive area | `ROOM_AREA_POSITIVE` / `UNIT_AREA_POSITIVE` |
| 12 | disconnected unit geometry | `UNIT_GEOMETRY_CONNECTED` |
| 13 | excessive tiny polygons / room explosion | `EXCESSIVE_ROOMS` |
| 14 | invalid topology (dangling graph edge) | `TOPOLOGY_VALID` |
| 15 | missing scale | `SCALE_PRESENT` |
| 16 | missing elevation | `ELEVATION_PRESENT` |
| 17 | missing building association | `BUILDING_ASSOCIATION_PRESENT` |

The Python-side report and the Node association-level issues are merged into
one `validation: { status, counts, issues }` on the stored `aiFloorPlans`
document and returned by `GET /api/ai/floorplans/:id/validation`.

## 10. Reusing Phase 2 `geometry3d` (no second volume system)

Every AI unit's WGS-84 polygon (when georeferenced) is passed straight into the
**existing** `services/geometry3d` module — the same `volumeFromFootprint()`
used by buildings/floors/units in Phase 2 — producing the same
`{ volumeId, xmin, xmax, ymin, ymax, zmin, zmax, geometryVersion, source,
prototype, label }` shape. `zmin`/`zmax` are set **only** when a real floor
elevation/height is known; otherwise both stay `null` (`heightStatus:
"UNAVAILABLE"`), never fabricated. When a floor height is available, the value
is explicitly labelled `heightStatus: "ESTIMATED"` (never "survey-grade").
Containment is checked with the **existing** `validateUnitVolume()` (same
`GEOMETRY_TOLERANCE_M` tolerance, same `UNIT_INSIDE_BUILDING` rule) — no
duplicate validation logic was written. A non-georeferenced unit keeps its 2D
`localBoundary` (pixel/metre polygon) separately; an axis-aligned box is never
presented as an exact apartment boundary when the shape is irregular.

## 11. 3D extrusion

```
Floor Plan Polygon (pixels)
  → Node bbox-fit onto building footprint → 2D Unit Polygon (WGS-84)
  → Floor Elevation (existing floors record, or null)
  → Floor Height (existing floors record, or null)
  → 3D Unit Volume (Phase-2 volumeFromFootprint)
```

If floor height is unavailable, no height is invented — the volume's
`zmin`/`zmax` stay `null` and the Cesium layer falls back to a fixed, clearly
labelled `ESTIMATED_AI_UNIT_HEIGHT_M = 3` slab (mirrors the Phase-3
`ESTIMATED_AI_HEIGHT_M` pattern) so the unit is still visible in 3D, never
implying a survey-grade height.

## 12. Cesium integration — ONE viewer, unchanged hierarchy

**No second viewer. No per-building, per-floor or per-locality map.** Everything
is added to the existing `Cesium3DMap.jsx`:

- New layer **"AI Floor Plans / Property Units"** (`LayerManager`, group *AI
  Extraction*). `DEFAULT_LAYERS.aiFloorUnits = false` — **OFF by default**.
- `ensureAiFloorUnits(areaId)` — lazy per area, idempotent (guarded by
  `aiFloorUnitId`), re-run on every `flyToArea` (mirrors
  `ensureAiBuildings` from Phase 3) so a fresh segmentation appears without a
  reload. Only **georeferenced** units (with a real building/floor reference)
  are placed on the map — local-only floor plans stay on the AI Floor Plan page.
- **Progressive loading**: AI floor-plan units render only at the `building`
  LOD (not `city`, not `area`) unless the unit is the one currently selected —
  the existing camera-height LOD bands (`installLod`) are untouched, and the
  Chennai-wide / area views never render room/unit geometry, per spec §22.
- Picking an `ai-floor-unit` entity → `selectAiFloorUnit()` → the existing
  `PropertySidebar` renders a new `AiFloorUnitCard` (composition, confidence,
  geometry/validation status, 3D volume, building/floor/parcel association,
  review workflow) — the same show/hide/isolate pattern as every other
  selection mode, so picking stays intact.
- Hierarchy is unchanged and now includes the AI layer as a sibling of the
  existing Property-Unit path: `Chennai → Area → Parcel → Building → Floor →
  Apartment/Unit → Room`. Users can select a building, drill into a floor,
  select an apartment (demo or AI), isolate it, inspect it, and return to
  floor/building/Chennai exactly as before.

## 13. Apartment isolation

Selecting an AI unit shows its boundary + 3D volume and (via `roomDetails` on
`GET /api/ai/floor-units/:id`) its member rooms in the sidebar. "Isolate Unit"
reuses the same `isolated` flag as the demo Property Unit card — other AI units
are hidden while isolated, nothing is destroyed, and picking is preserved.
`data-testid="ai-floor-unit-isolate"` / `ai-floor-unit-card` /
`ai-floor-unit-review-status` mirror the Phase-3 testid conventions.

## 15. MongoDB

Three **new** collections — no change to any existing collection, `floors`,
`propertyUnits`, or the seed:

- **`aiFloorPlans`** — one document per inference job: model/dataset
  provenance, `crs`/`coordinateReference`/`scaleMPerPx`, `buildingId`/`floorId`
  association, `topology`, `walls` summary, `validation`, `summary`,
  `reviewStatus`.
- **`aiRooms`** — one per detected room: `class`/`roomType`, local polygon,
  area (+ unit/status), confidence, `geometryStatus`, `source: "AI_DEMO"`.
- **`aiFloorUnits`** — one per inferred apartment/unit: member `rooms[]`,
  `localBoundary` + (if georeferenced) WGS-84 `geometry`, the Phase-2
  `volume` block, `volumeValidation`, `parentParcelId`/`parentULPIN` (an
  **existing** Phase-1 ULPIN, never invented) with `ulpinStatus:
  "DEMO_NOT_OFFICIAL"`, confidence, review workflow.

## 16. Evaluation & domain shift

`scripts/evaluate_floorplans.py --images DIR --masks DIR` reports WALL-mask
IoU / Precision / Recall / F1 / Dice plus a mean room-count absolute error
against ground-truth class masks. **CubiCasa5K accuracy ≠ Chennai accuracy.**
CubiCasa5K is predominantly Finnish residential floor plans — different
notation/symbols, room-mix conventions, drafting conventions, scan quality and
apartment typologies than Chennai. Any real Chennai deployment needs separate
validation against Chennai-labelled floor plans; until then all dataset-derived
output stays `DEMO_RESEARCH_DATA`.

## 18. Limitations (explicit)

1. CubiCasa5K is not Tamil Nadu cadastral data.
2. AI predictions are not legally authoritative.
3. Floor-plan image scale may be unavailable — areas then report
   `PIXEL_SQUARED` with `areaStatus: "SCALE_UNAVAILABLE"`, never a false metric.
4. Geographic placement requires a valid building/floor reference; without one,
   geometry stays local and is not shown on the map.
5. Building/floor height may be estimated (`heightStatus: "ESTIMATED"`), never
   claimed as survey-grade.
6. Apartment boundaries are AI-inferred from room adjacency — not a legal
   survey of unit ownership boundaries.
7. AI can misclassify rooms — the classical heuristic caps its own room-type
   confidence and flags most rooms `reviewRequired: true`.
8. Walls may be incomplete or noisy, especially at low scan resolution.
9. Doors/windows may be missed by the classical segmenter (it detects openings
   geometrically; a trained model with the `cubicasa5k-icons` vocabulary
   improves this — see §3).
10. Irregular units are kept as their true 2D polygon (`localBoundary` /
    `geometry`); the Phase-2 volume box is an axis-aligned approximation of
    that shape, not a perfect fit — the sidebar never claims otherwise.
11. Domain shift exists between CubiCasa5K (research dataset) and real Chennai
    floor plans — see §16.
12. Human review is required for any authoritative use — every AI floor-plan
    document defaults to `reviewStatus: "REVIEW_REQUIRED"`.
13. This module **never** generates an official ULPIN, survey number,
    ownership record, or government-approved apartment boundary.

## 19. Out of scope (later phases)

LiDAR integration, GNSS/CORS height integration, DEM/DSM processing, legal 3D
property rights, official 3D ULPIN generation, government cadastral
synchronisation, PostGIS migration, QGIS automation, national deployment,
production government data integration.
